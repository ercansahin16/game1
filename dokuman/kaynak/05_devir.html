19.2 Firebase'i yeni bir projeye taşımak gerekirse

Proje sahipliği devri yeterliyse buna gerek yoktur. Yeni bir Firebase projesine veri taşımak istenirse (örneğin yeni Gmail altında sıfırdan proje):

  1. Yeni projede Authentication (E-posta/Şifre + Google) ve Firestore'u açın; Güvenlik Kurallarını eski projeden kopyalayın.
  2. Kullanıcı hesapları: Firebase CLI ile firebase auth:export hesaplar.json --project eski ve firebase auth:import hesaplar.json --hash-algo=... --hash-key=... (parola özeti parametreleri, eski projenin Authentication → Kullanıcılar → ⋮ → "Password hash parameters" bölümünden alınır). Bu yapılmazsa kullanıcılar şifresiz kalır ve "şifremi unuttum" ile yeniden belirlemek zorunda kalır. Uid'ler korunmalıdır, çünkü users/{uid} belgeleri uid'e bağlıdır.
  3. Firestore verisi: Spark planda yönetilen dışa aktarma (export) yoktur. Admin → Veri Yönetimi → "Tüm Verileri Yedekle" ile indirilen JSON veya duzenler.html → Yedek İndir / Yedekten Geri Yükle kullanılır. Yedek dosyasının kullanıcı koleksiyonunu eksiksiz kapsadığını önce test projesinde doğrulayın.
  4. firebase.js dosyalarını (saadetyolu, test, gerekiyorsa admin/duzenler) yeni projenin yapılandırmasıyla güncelleyin. Önce test klasöründe deneyin, sonra canlıya geçin.
  5. Firebase Authentication yetkili alan adlarına nevafil.com.tr'yi ekleyin.

20.2 Önerilen iyileştirmeler (öncelik sırasıyla)

  1. Firestore kurallarını inceleyin ve depoya kaydedin. Hangi koleksiyonun kime açık olduğunu tablo olarak çıkarın (bölüm 13 başlangıç noktasıdır). Yeni kuralları önce ayrı bir test Firebase projesinde deneyin (geliştiricinin planı budur).
  2. Admin için gerçek giriş: Admin'e Firebase Authentication ile e-posta/şifre girişi ekleyin ve kurallarda yönetici ayrıcalığını request.auth.token.email == "..." veya özel talep (custom claim) ile verin. Böylece şifre kodda durmaz ve kurallar kimliksiz yazmaya izin vermek zorunda kalmaz. Aynı değişiklik duzenler.html için de yapılmalıdır.
  3. Herkese açık sıralama koleksiyonu: Sıralama için gereken alanları (ad, ID, puanlar, seviye, çevrimiçi) ayrı bir leaderboard/{uid} belgesine yazın; users belgelerini yalnızca sahibine (ve yöneticiye) açın. Böylece e-posta ve mesajlar diğer kullanıcılardan gizlenir.
  4. Misafir destek için koruma: Mesaj boyutu ve alan doğrulaması kuralları, Firebase App Check (reCAPTCHA) ve gerekirse mesaj başına kimlik doğrulama.
  5. Firebase API anahtarı kısıtı: Google Cloud Console → API ve Hizmetler → Kimlik Bilgileri → anahtar → "HTTP yönlendiren" kısıtı: nevafil.com.tr/* ve geliştirme adresleri.
  6. ntfy: Kendi yetkilendirmeli ntfy sunucusu veya yönetici erişimli konu.
  7. Düzenli yedek: Ayda bir Admin → Veri Yönetimi yedeği, güvenli yerde saklama (içinde kişisel veri vardır).
Güvenlik düzeltmeleri canlıya doğrudan uygulanmamalı; kural değişikliği tüm kursiyerlerin girişini veya yazmasını kırabilir. Önce test projesinde, ardından kısa bir bakım penceresinde yapılmalıdır.

20.3 Kişisel veri ve gizlilik notları

  • Saklanan kişisel veriler: ad soyad, e-posta, (misafir desteğinde) telefon/e-posta, ilerleme verileri, mesajlar. Telefon numarası ve e-posta ntfy bildirimine konmaz.
  • Soru/Hata'da e-posta ve cihaz bilgisi herkese açık belgede değil, yalnızca yöneticinin okuyabildiği belgede tutulur.
  • Admin "hesabı sil" işlemi profilin yedeğini deletedUsers koleksiyonunda bırakır; kalıcı silme istenirse bu belge de silinmelidir.
  • Arkadaşlık mesajları serbest metin değil, hazır mesajlardır; kötü içerik oluşması engellenmiştir.
  • Duyuru resimleri Cloudinary'de herkese açık adreslidir; kişisel resim yüklenmemelidir.
